## Verifying a release

Releases are signed **keylessly** with [Sigstore](https://www.sigstore.dev/): there is no
private key and no signing secret in the repository. The release workflow exchanges its
short-lived GitHub Actions OIDC token for an ephemeral certificate, signs with it, and the
signature is recorded in the public Rekor transparency log. The certificate binds the
signature to *that workflow, in that repository, at that tag* — which is exactly what the
command below checks.

You need [cosign](https://docs.sigstore.dev/cosign/system_config/installation/) v3 or newer.
Nothing else: no key to fetch, no keyring to trust.

Signing starts with **{facts.releases.signingStartsAt}**. Earlier releases carry no signature
bundle, and {facts.releases.noAssets} has no assets at all — its release run failed before the
artifacts were produced. Use {facts.releases.signingStartsAt} or later. The
[security policy](/evaluate/security-policy/#verifying-a-release) has the full detail,
including why checksums alone prove nothing about origin.

<Aside type="note" title="v0.3.1 named its bundles differently">
v0.3.1 published its signature bundles as `<asset>.cosign.bundle`. The bytes were already
the standard Sigstore bundle format — only the extension was non-standard, which meant no
tool looking for signatures by filename could find them. From the next release onwards the
same bundles are named `<asset>.sigstore.json`. To verify v0.3.1, substitute
`.cosign.bundle` for `.sigstore.json` in the command above; nothing else changes.
</Aside>

## Build provenance

From the release after v0.3.1, each release also carries **SLSA build provenance** as
`fednow-oss-<tag>.intoto.jsonl`. A signature tells you *this workflow, at this tag, signed
these bytes*. Provenance is a machine-readable in-toto statement telling you *these bytes
were produced by this workflow run, from this commit* — the form a policy engine can
evaluate, rather than a human comparing a certificate identity by eye.

It is checked with the [GitHub CLI](https://cli.github.com/) rather than cosign:

```console
$ gh attestation verify "fednow-oss-$TAG-x86_64-linux.tar.gz" \
    --repo joaoabuenosi/fednow-oss \
    --signer-workflow joaoabuenosi/fednow-oss/.github/workflows/release.yml
```

`--signer-workflow` is the load-bearing flag: `--repo` on its own would accept an
attestation from any workflow in the repository. Add `--bundle fednow-oss-$TAG.intoto.jsonl`
to check against the downloaded asset instead of GitHub's attestation API. The
[security policy](/evaluate/security-policy/#verifying-build-provenance) has both forms.

## OpenSSF Scorecard

[![OpenSSF Scorecard](https://api.scorecard.dev/projects/github.com/joaoabuenosi/fednow-oss/badge)](https://scorecard.dev/viewer/?uri=github.com/joaoabuenosi/fednow-oss)

The [OpenSSF Scorecard](https://securityscorecards.dev/) runs {facts.cadence.scorecard} and on
every push to <code>{facts.cadence.scorecardPushBranches.join(', ')}</code>, publishes to the
public OpenSSF API, and uploads its findings to the repository's code scanning tab. The badge above is served by OpenSSF, not by this site — it shows the
current score whether or not that score is flattering.

Raising it is ongoing work rather than a finished job: the most recent step was
[#84](https://github.com/joaoabuenosi/fednow-oss/pull/84), which pinned every third-party
action to a commit SHA and scoped every workflow's permissions, and the checks still
counting against the score are being closed the same way.

<Aside type="tip" title="Pinning is enforced, not just claimed">
Every third-party action in **every** workflow is pinned to a 40-character commit SHA
carrying a `# <version>` comment, and every workflow starts from `permissions: {}` with
per-job scopes. Neither is a promise someone has to remember to keep: both are checked on
every CI run by
[`check-workflow-hardening.sh`](https://github.com/joaoabuenosi/fednow-oss/blob/main/.github/scripts/check-workflow-hardening.sh),
which fails the build if a workflow gains an unpinned `uses:` or loses its top-level
`permissions:` key. Read it at the source in
[`SECURITY.md`](/evaluate/security-policy/#practices), or check the
[workflows themselves](https://github.com/joaoabuenosi/fednow-oss/tree/main/.github/workflows).
</Aside>

## Reporting a vulnerability

Do **not** open a public issue for a security problem.

- Preferred: [GitHub private vulnerability reporting](https://github.com/joaoabuenosi/fednow-oss/security/advisories/new) —
  the "Report a vulnerability" button under the repository's *Security* tab.
- If you cannot use GitHub: email the maintainer with the subject given in the policy.

Acknowledgement within **72 hours**, a triage verdict within **7 days**, fix timelines agreed
case by case. Credit in the release notes and a CVE where applicable, unless you would
rather stay anonymous. The [full policy](/evaluate/security-policy/#reporting-a-vulnerability)
has the scope notes, including what is explicitly out of scope.

## Talk to the maintainer

Pacsmith is built and maintained by one person, in the open. If you are at a bank or a
credit union weighing this up, these conversations are welcome — and genuinely useful,
because they are what decides what gets built next:

- **Evaluation questions.** Anything on this page that is not specific enough for your
  sign-off: the supply chain, the licence, the disclosure process, or what is actually
  implemented today versus what is still on the roadmap.
- **Pilots.** Standing the gateway and the simulator up against your own environment, and
  working out what would have to be true before any of it went near production. It is
  {facts.status.lowerLabel} software; that conversation starts from there, not around it.
- **Design partners.** The simulator is being packaged as a certification-readiness kit
  ([#79](https://github.com/joaoabuenosi/fednow-oss/issues/79)) — a local rehearsal of the
  Customer Testing Program's scenarios, run on your own machines before you book operator
  time. Institutions that will actually run those scenarios get to shape it.

Three things worth stating plainly, because evaluators ask:

- **No telemetry, no phone-home.** The software does not report anything anywhere. Nothing
  you run reports back to this project, ever.
- **The website counts page views, and that is all it does.** It uses Vercel Web Analytics:
  privacy-friendly, cookieless page-view counts. No cookies — none, from anything on this
  site. No personal data and no IP addresses stored, nothing written to your device by the
  analytics, and so no consent banner. It is first-party: both the script and the endpoint
  it reports to are served from this domain under `/_vercel/insights/`, never a
  third-party host. The only third-party request this site makes is the OpenSSF badge
  above, fetched from OpenSSF. Two things stated rather than glossed: the site is hosted
  by Vercel, which already serves every request to it, so this adds a count and not a new
  party — and the site does keep two **local preferences** in your browser (the light/dark
  theme you picked, and which sidebar sections you left open). They never leave your
  browser, identify nobody, and are listed by name on [About](/about/#privacy).
- **No credentials in the repository, ever** — no certificates, no live endpoints, no real
  routing numbers or institution names. Test fixtures use fictitious identifiers.
